# Dependency provenance

Current selection policy does not gate a locally selected app on repository app-version, runtime-version, or component-hash allowlists. macOS validates the official bundle/team identity and signatures, supported arm64 architecture, runtime platform/architecture, required files, and a recognized original Codex CLI/code-mode-host pair, then reuses the app in place. The current app check accepted ChatGPT `26.924.22138` with CUA runtime `0.0.24/20260924074400-f52ea85e2a98`; see [current macOS verification](verification/macos-current-app-2026-09-26.md). Linux local selections use package identity, architecture, structural checks, and managed-tree inventory. The default remote Linux download still verifies its official-source SHA-256 from `runtime.lock.json`. Windows selection validates the registered official Store package identity, publisher/signature, architecture, and required structure, then records a source-derived inventory for the private copy. This policy description adds no new Windows live verification or support claim.

Historical Windows source specimen: the inspected Store MSIX had SHA-256 `9892383820c5505997456bde8385810afadd6076ae7fff9e3835a48ca0555c98`. Its `app/resources/app.asar` member `.vite/build/main-BR_2NHW6.js` had SHA-256 `1f2b91cf92fc023fb2fa41e1c1d03698fa6e37354ecd07dd0cebd21337607b08`; byte range `[155346,165208)` was the original `Wre` native-pipe host (SHA-256 `3dae7a2bb89573e78dff25715efaf44dadbe7a7376c9243987d18d43b5f05247`). These hashes describe inspected source evidence, not the current app-selection allowlist. The Windows installer validates the selected app structure, extracts the required original host members, and records the complete source-derived inventory for its private copy. A thin entry starts and disposes the host outside the original sandboxed Node REPL. The original helper, Sky service, pipe protocol, approval forwarding and CUA API stay unchanged; none of those extracted bytes enters Git or a thin archive.

The original app's `Noe` handler calls `Wre.closeActiveTurn({sessionId,turnId})` directly on app-server `turn/completed`; the standalone Node REPL and host are separate processes. LCU's Windows trusted-service wrapper forwards `nodeRepl.rpc('sky',...)` to the unchanged original Sky service, registers the original `addTurnEndedHandler`, and uses the original `nodeRepl.nativePipe` facility to send only real session/turn IDs over a random private lifetime pipe. The host calls unchanged `closeActiveTurn`; this signal neither routes CUA methods nor grants access. Installed candidates listed a live Notepad window and saved exact Unicode text to an existing file with an independent byte oracle. A matching Stop removed its helper, a stale Stop left a newer turn's helper intact, a matching Interrupt removed that helper, and MCP shutdown removed a third helper. The original `turn_ended` tool returned `{}` even when an earlier callback failed, so this conclusion rests on the independent helper-state oracle. See [Windows source evidence](verification/windows-source.md) for the guest boundary.

The historical Linux source package inspected for the earlier host tests was ChatGPT `26.915.31945`, with CUA runtime `0.0.16/20260915001755-492f19756c31`. `runtime.lock.json` retains that package URL template, architecture-specific download SHA-256 digests, and critical-file hashes. The default remote download checks its SHA-256 before extraction; this verifies that acquisition input, not the compatibility of a locally selected app and not independent package-signature authentication. Locally supplied `--app-package`/`--existing-app` selections are checked by Debian package identity, architecture, required structure, and known host layout, then protected as managed copies by their recorded full-tree inventory.

The inspected .deb control metadata says Package=chatgpt, Version=26.915.31945, with Architecture=arm64 or amd64. The historical app lived at usr/lib/chatgpt and contained the unchanged resources/cua_node runtime, resources/codex and resources/codex-code-mode-host, plugin tree, Electron application and original notices. LCU stages the complete selected package payload under a managed prefix and records the observed version/runtime plus a deterministic full-tree inventory digest. It does not run package maintainer scripts or register the app with apt.

The inspected package post-install script writes an OpenAI apt key/source and loads an AppArmor profile. That profile is bound to /usr/lib/chatgpt/ChatGPT, the original Electron UI executable, and grants userns to it. LCU launches the selected app's Node/REPL directly, without running that post-install script. Ubuntu 24.04.5 ARM64 and x86-64 guests with AppArmor active passed installed native fixtures and no-sign-in Chrome actions using LCU's relay; the x86-64 guest ran under KVM on physical AMD hardware. Process sampling found Node/REPL `unconfined`, Chrome and the extension host `chrome (unconfined)`, and nonblocking `bwrap` capability denials. Chrome launched without `--no-sandbox`. See the [exact verification record](verification/installed-app-2026-09-23.md).

The original Chrome provider and native messaging host come from `resources/plugins/openai-bundled/plugins/chrome` in this same installed app. Its `scripts/installManifest.mjs` registers native messaging; LCU copies that plugin to the target account's writable data directory during browser setup, runs the original installer there, and points the account's manifest at LCU's small relay. The relay locally enables the official extension's agent request label. The original `docs/chrome-troubleshooting.md` lines 31–38 directs a missing-extension user to the selected browser's exact `storeUrl` in `scripts/extension-ids.json` and requires permission before opening the store or management page. It provides no silent Web Store installation action; the desktop user must confirm installation or enablement in the browser. LCU prints the same official store link and preserves that browser confirmation boundary. [OpenAI's extension documentation](https://learn.chatgpt.com/docs/chrome-extension) gives its supported setup flow. [Google's Chrome Linux guide](https://support.google.com/chrome/answer/95346?hl=en) lists both x86-64 and ARM64 packages. Extension discovery alone does not prove browser action.

The shared harness client uses `@modelcontextprotocol/sdk` 1.30.0, pinned in `adapters/package-lock.json`; it delegates MCP protocol behavior to that SDK. The Pi extension uses the host Pi installation.

The build fetches separately pinned third-party agent registration tools defined in scripts/agent-tools/package-lock.json. Their temporary build Node is discarded; setup uses the selected official app Node. These tools and LCU code may appear in a thin archive, subject to their own licences. Original OpenAI app binaries, runtime packages, documents and generated fragments must not. The copied full-bundle source was removed from the working tree. The full-copy commit was removed from the new local main lineage, and its remote feature branch was deleted.
