# Fresh macOS guest verification, 2026-09-24

This is an **in-progress** isolation check. A fresh guest has been installed, but the original CUA helper has not been launched in it, so this does not prove cold startup or first-use macOS permissions.

## Disposable guest and staged inputs

UTM 4.7.5 created only a new Apple Virtualization VM named `LCU macOS cold helper test` using UTM's automatic Apple IPSW download (`UniversalMac_26.6.2_25G83_Restore.ipsw`). The VM has 8 GiB RAM, 4 CPUs, and a 64 GiB sparse disk. Existing VMs, the user's installed Codex helper, and host TCC state were not changed. The guest installed macOS 26.6.2 and is currently at Setup Assistant's **Select Your Country or Region** screen, with France selected and Continue enabled. The VM remains running. Host free space was 48 GiB after the install.

The host-only staging directory `/private/tmp/lcu-mac-guest-staging-20260924` contains only the copied original signed `/Applications/ChatGPT.app` 26.917.62051, the thin `lcu-0.3.0-darwin-arm64.tar.gz` built from source commit `69f7433` (SHA-256 `c0613fbc50ecb5c60fef88f552b9c3c3ef3a8847f08ee31df1c00c6b45df7589`), and the official Python.org 3.13.15 macOS installer (SHA-256 `3b7eaf7f29825f796e8267024435540ddf1f17fc9a97ad58095daa7a75bfdcd3`). The copied app passed `codesign --verify --deep --strict`; the Python package hash matched the [Python.org release](https://www.python.org/downloads/release/python-31315/) and `pkgutil --check-signature` identified the Python Software Foundation Developer ID Installer. No host home, authentication, helper socket, or TCC files are staged. The thin archive contains no upstream app/runtime payload.

UTM's documented `update registry` command attached that staging directory to the exact new VM. A fresh registry read returned only `file Macintosh HD:private:tmp:lcu-mac-guest-staging-20260924:`. [UTM's macOS guest guide](https://docs.getutm.app/guest-support/macos/) documents mounting the share inside a macOS 13+ guest with `mount_virtiofs share` after login. This does not establish that the guest has mounted or read the directory yet.

The same task-only share now also contains `guest-install.sh`, `guest-first-use.py`, and the repository's small `mcp_client.py` test transport. The install script syntax and Python scripts' parse were checked on the host but none has run in the guest. After login, the intended guest Terminal command is `sudo mkdir -p /Volumes/LCUShare && sudo mount_virtiofs share /Volumes/LCUShare && bash /Volumes/LCUShare/guest-install.sh`. The script checks package hashes, copies the signed app to guest `/Applications` with `ditto`, verifies its signature, installs the official Python package, and selects the original app using the thin LCU runtime-only installer. It does not launch the helper. The separate `guest-first-use.py` makes the first LCU `cua.getApp('com.apple.TextEdit')` call with an app-scoped MCP test approval, leaving macOS permission prompts visible for explicit guest-local decisions.

## Setup Assistant input boundary

Host LCU using the original `@oai/cua` API can observe the UTM VM window and send `utm.pressKey(...)`. The key input selected France in the guest's region list, and Tab moved focus between the region list and Back arrow. Original LCU `utm.click([x,y])` on the guest view returned `Computer Use server error -10005: noWindowsAvailable`; the AX tree exposes only UTM's own window, toolbar, and menus, with no indexed guest viewport. Return and Space did not activate the enabled Continue button. Apple's [keyboard shortcut reference](https://support.apple.com/en-il/102650) documents Control-F7 to switch Tab focus between all controls and only lists/text; sending that shortcut through original LCU and repeating Tab/Space still did not activate Continue. These are observations of the original host CUA/UTM path, not a demonstrated LCU adapter difference.

UTM's [AppleScript input automation reference](https://docs.getutm.app/scripting/reference/) explicitly limits guest mouse and keyboard commands to the QEMU backend; the exact `input mouse click` call against this Apple-backend VM returned `Operation not supported by the backend (-2700)`. A task-scoped System Events query from the host execution context reported UTM `frontmost=false, windows=0` even after `activate`, so it supplied no addressable guest view. Input retries were stopped. The smallest manual step is to click the visible enabled **Continue** button in UTM's `LCU macOS cold helper test` guest region screen. Later Setup Assistant controls may also require direct guest clicks.

One later documented accessibility route was checked. Apple describes [Command-F5 to toggle VoiceOver](https://support.apple.com/guide/voiceover/turn-voiceover-on-or-off-vo2682/10/mac/27) and [VO-Right Arrow / VO-Space to navigate and activate controls](https://support.apple.com/guide/voiceover/control-your-mac-with-keyboard-commands-vo2681/10/mac/27). Original LCU `utm.pressKey('super+F5')` produced no visible guest VoiceOver cursor, caption, welcome UI, or focus change; a single `ctrl+alt+Right` likewise produced no visible change. The same Command-F5 was sent again to attempt to restore the prior accessibility state, and no further input attempt was made. Because there was no visible indicator, the guest VoiceOver state was not independently verified. This route did not advance Setup Assistant.
