# Claude Code lifecycle boundary and manual probe

LCU currently registers the original MCP server and generated skill in Claude Code. It does **not** register a lifecycle hook. This is an explicit integration limit: the original CUA plugin calls its hidden `turn_ended` tool on `Stop`, `Interrupt`, and `SubagentStop`, passing both `session_id` and `turn_id`. The selected app's source is `plugins/openai-bundled/plugins/unified-computer-use/.codex-plugin/plugin.json`; LCU's adaptation is in `lcu/codex_hooks.py`.

Claude Code's official [hook reference](https://code.claude.com/docs/en/hooks), checked 2026-09-25, says `Stop` runs when the main agent finishes but **does not run on user interrupt**; API errors use `StopFailure`. `SessionEnd` runs when the whole session exits, with no per-turn interrupt reason. [MCP tool hooks](https://code.claude.com/docs/en/hooks#MCP-tool-hook-fields) can call an already-connected server and interpolate hook input. The documented [common hook input](https://code.claude.com/docs/en/hooks#common-input-fields) and [Stop input](https://code.claude.com/docs/en/hooks#stop-input) supply `session_id` but not `turn_id`. The [MessageDisplay input](https://code.claude.com/docs/en/hooks#messagedisplay-input) has `turn_id`, but fires only when assistant text is rendered and cannot identify every tool-only computer-use turn. More fundamentally, normal Claude Code CLI has not been shown to attach that same ID pair to its original MCP calls. Installing a Stop hook with `${turn_id}` would therefore assume both an undocumented field and unproven request correlation. No documented ordinary-CLI event provides reliable cleanup immediately after a user interrupts a still-open session. These are limits of the reviewed hook contract and installed version, not a claim about every future Claude version. The installed Claude Code 2.1.204 native binary contains `MessageDisplay`, `StopFailure`, and `SessionEnd` event strings but no `UserInterrupt` string; this string inspection is corroborating evidence, not a live event test.

The original Chrome `browser-service.mjs` is one concrete cleanup consumer: its `TurnEndedTracker` registers `addTurnEndedHandler`, records matching browser `session_id` and `turn_id` on extension/CDP/IAB requests, and invokes browser callbacks when that pair ends. The service throws if a browser request lacks either identifier. The Windows native pipe host is another lifecycle consumer: the pinned original `Wre.closeActiveTurn` matches that ID pair and closes the native helper. An installed LCU candidate proved that direct matching Stop and Interrupt calls remove helpers, while a stale Stop leaves a newer turn intact. Claude Code registration does not dispatch those calls on either normal completion or interruption. Linux/macOS native-only runs do not establish Windows behavior; Windows native and Chrome opt-in both lack Claude's correct per-turn cleanup.

The original MCP server advertises `turn_ended` and `js_add_node_module_dir` alongside `js` and `js_reset`. LCU's Codex registration applies the original host visibility policy, but its direct Claude registration has no equivalent filter. Claude's [CLI reference](https://code.claude.com/docs/en/cli-reference) says a bare `--disallowedTools` rule removes matching tools from model context; [settings](https://code.claude.com/docs/en/settings) supplies the corresponding `permissions.deny` list. LCU's focused Claude settings adapter adds exact deny rules for those two host-only names while preserving other settings. Whether installed Claude 2.1.204 actually hides them is a manual probe gate under the local launcher guard.

The official [Claude Agent SDK](https://github.com/anthropics/claude-agent-sdk-typescript) has a V1 streaming `Query.interrupt()` control. An SDK launch adapter could own the interrupt decision, but it would be a separate headless program rather than the normal interactive `claude` CLI. It would also need an MCP bridge to stamp one turn ID across original `js` calls and forward images and elicitation. Anthropic's [SDK V2 interrupt issue](https://github.com/anthropics/claude-agent-sdk-typescript/issues/120) records that its preview session interface lacks `interrupt()`. No SDK adapter is shipped or claimed here. This machine's Claude launcher deliberately blocks automated runs, and using the SDK's bundled executable would evade that guard.

## Prepared manual falsification

The probe writes only to a new private temporary project. It generates the selected app's full local skill in that project, registers an LCU MCP command there, installs the two exact host-only deny rules, and installs project-local hooks that log only event names and session IDs. It never starts Claude, copies account credentials, records prompts, or changes personal Claude settings.

```sh
python3 tests/claude_lifecycle_probe.py prepare \
  --release /absolute/path/to/installed/lcu/current \
  --output /private/tmp/lcu-claude-lifecycle-probe
cd /private/tmp/lcu-claude-lifecycle-probe/project
# In the owner's interactive shell, intentionally start the guarded `clod` launcher.
```

Once Claude starts, confirm the project MCP and skill are visible. Give it this normal-completion task: “Read the local LCU skill. Use LCU's original `js` tool to evaluate `1+1` and then `2+2` in separate calls, and report both results. Do not use the desktop or browser.” After it finishes, inspect `../events.jsonl` for `PreToolUse`, `PostToolUse`, and `Stop` with one session ID.

Then give it this interrupt task: “Use LCU `js` to set `globalThis.lcuProbe = 7`, then in a separate `js` call wait for 30 seconds before reporting the value. Do not use the desktop or browser.” Once the waiting tool call starts, interrupt Claude using its normal interactive control. Inspect the new lines in `../events.jsonl`; any `Stop`, `StopFailure`, or other event that runs immediately on interrupt would change the source-only conclusion. A missing event confirms this installed version cannot notify the original CUA server at that point through hooks. The probe does not claim a live Claude result until a person deliberately runs it and records the output.

The recorder itself was checked with a synthetic hook payload: it wrote only `{"event":"Stop","session_id":"session-1"}` with file mode `0600`, discarding a supplied prompt and transcript path. `prepare` succeeded against the installed macOS LCU release at `/private/tmp/lcu-delivery-install/current` without launching Claude.

## Live guarded check, 2026-09-25

The frozen Darwin ARM64 archive from source `66bb0fb0dd2235dd83ab35e7ac468a985fc0b77f` (SHA-256 `a56cc54b0c45d214391c349e4a161d7458c090c246db159d670344ad3b0392bd`) installed its runtime-only adapter against the existing signed ChatGPT app. The selected runtime reported ChatGPT `26.917.62051` and CUA `0.0.16`; the guarded interactive launcher reported Claude Code `2.1.204`. After accepting project trust and the project-local LCU MCP server, `/mcp` showed LCU connected with four tools. Its server-tools view listed `js`, `js_add_node_module_dir`, `js_reset`, and `turn_ended`. The probe's project settings contain exact deny rules for the two host-only tools, but the `/mcp` listing is the server inventory, not proof of model-context filtering.

The sandboxed launch first failed Claude's `SessionStart` hook with an `EPERM` while creating its own session directory and showed `ConnectionRefused`. A guarded PTY launch with normal host permissions passed startup; its first prompt reached the configured provider and returned HTTP 403, stating that the account had migrated to a new provider site. No account login, provider change, credential entry, or LCU computer-use call was made. The bounded live sequence therefore stopped before the two successful JavaScript calls or the long-call interrupt.

The private mode-0600 event log contained `SessionEnd` for the first launch, then `StopFailure` and `SessionEnd` for the API-error session. It contained no `PreToolUse` or `PostToolUse` events because no MCP tool call ran. These observations confirm the installed hook recorder executes for session end and API failure; normal `Stop`, MCP tool filtering in model context, `turn_ended` correlation, and interrupt cleanup remain unverified.
