### What the request header does

The pinned original browser service fetches `https://chatgpt.com/backend-api/aura/identity` through its trusted fetch interface, requires a user ID, initializes Statsig for that user, and reads the `codex_browser_use_agent_request_header` feature gate. It fails if the gate is unavailable or unrecognized. The official extension reports `agentRequestHeaderEnabled` from its local state; on a fresh profile this is `false`, which makes the browser service read the gate on the first relevant session request. If the extension already reports `true`, the browser service keeps it enabled without another gate lookup on that path. The service sends `agent_request_header_enabled` to the extension with relevant session requests. Once enabled, the extension stores the decision in Chrome's local storage and adds `x-browser-agent: ChatGPT/<session ID>` to requests from agent-controlled tabs using Chrome's `declarativeNetRequest` rules. The label is visible to destination websites. It is not a bearer credential, ChatGPT login cookie, or signed proof of agent identity. Sources inspected: `resources/plugins/openai-bundled/plugins/chrome/scripts/browser-service.mjs` in the pinned app and `background.js` in official extension CRX 1.26.901.11451 (SHA-256 `688d5c0a8141c9bee394d3738d4a177b448713c2fa9c29b5af1815bfddae46e1`).

The code establishes the mechanism, not OpenAI's product rationale. Our inference is that the header labels agent traffic and the user-specific gate controls its rollout. [OpenAI's extension documentation](https://learn.chatgpt.com/docs/chrome-extension) describes feature rollout and workspace controls but does not explain this particular header. The earlier proposed adapter would have hidden the extension's `false` capability from the original browser service, preventing that service from obtaining and applying a possible `true` decision. It was not adopted.

A later disposable Ubuntu Chrome run placed a **pass-through-only** native messaging relay in the isolated fixture profile. It forwarded every message unchanged, reproduced the original authentication failure, and confirmed that the extension's `getInfo` reply carried `result.agentRequestHeaderEnabled: false`. An attempted test change to report `true` instead was rejected by automatic approval review before execution because the review did not find specific authorization for that mechanism. The user subsequently authorized that exact local override. Source inspection found no supported local setting that supplies the gate decision without identity: `BROWSER_USE_DISABLE_AMBIENT_NETWORK=1` skips identity initialization, but the request-header decision then fails with `Browser request-header policy requires caller identity.`
